# 多站点部署与高并发方案

本稿仅设计。需要同时支持源码独立部署到多个站点，以及一个后端为多个隔离站点服务。Docker Compose 是正式部署入口；高并发通过同一模块化单体的多副本、任务分离和数据库约束实现，不把单进程可启动当成扩容能力。

## 多站点的两种模式

| 模式     | 应用与数据库                                                             | 身份和配置                                    |
| -------- | ------------------------------------------------------------------------ | --------------------------------------------- |
| 独立部署 | 每个 Compose project 有自己的 app、数据库和 volume；可以同机不同内部端口 | 每站完全独立，版本和升级由各部署者控制        |
| 共享后端 | 共享 stateless app 集群；每站绑定独立 PostgreSQL 业务库与认证 realm      | 每站独立账号、密钥、session、管理员和业务配置 |

共享后端可以使用同一个 PostgreSQL cluster 中的多个 database，也可以指向不同托管数据库。核心内容在各站导入，管理员修订和用户数据属于该站；大型只读查词包可共享镜像资产。跨站转移学习数据必须使用用户明确发起的导出/导入，不因邮箱相同就自动合并。

选择独立业务库的理由是让认证的 email 唯一性、会话和业务数据在同一边界内。第一版不用“给某些业务表加 site_id”来替代认证隔离，也不依赖未验证的动态 ORM schema 技巧。成本是数据库/连接池数量和运营复杂度，需纳入连接预算。后续若改成共享表/RLS，必须作为单独迁移方案验收。

## 站点解析与配置

请求入口顺序是：验证代理来源 → 取得可信 Host/协议/路径 → 查询 SiteRegistry → 选择固定 realm/数据库 → 校验站点会话 → 执行业务。未知域名、非法路径或停用站点应拒绝，不自动新建数据库，不根据任意客户端 siteId 切库。

SiteRegistry 至少记录 siteId、域名别名、canonical URL、basePath、认证/数据库配置引用、启停状态、内容包与配置版本。部署操作者通过受控配置或管理 CLI 维护；站内 admin 只能改本站产品设置，不可修改连接串、其他站点域名或全局路由。

每站使用固定认证 realm、不同密钥和 Cookie prefix；Cookie 尽量 host-only，不设置共享父域 Domain。业务动作、导出、缓存、队列、日志和 IndexedDB 都绑定 siteId/userId。服务器从已验证入口决定 siteId，查询正文里的 siteId 不构成身份。

真正相互不信任的站点默认使用不同域名或子域。相同域名下不同路径可以提供部署兼容，但属于同一浏览器 origin，Cookie Path 不构成强租户隔离。子路径共存只用于同一信任域；品牌配置不允许任意 HTML/JS。页面、API 和认证的 site-bound 校验仍要执行。[同源规则](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy)，[Cookie Path 边界](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)。

## 域名与路径兼容

第一版验收 `https://learn.example.com/`、`https://example.com/study/` 和独立内部端口反向代理三种入口。以下路径全部由站点公开配置生成，不能保留旧工程里写死的根路径：

- Router basename、静态资源和动态加载路径。
- API、auth、登录返回地址、邮件链接与密码重置地址。
- PWA manifest start_url、scope、Service Worker 注册路径与缓存命名。
- Cookie path/prefix、站点公开 URL、对象存储与媒体 URL。

同一构建产物通过受控启动配置生成各站的 HTML bootstrap 和资源前缀；API 客户端不依据不可信的浏览器 query 参数推导服务器。深链接刷新只回退到本站入口，不能吞掉其他项目的 `/api` 或页面。SW 只控制本挂载路径，不缓存身份接口或另一站点的个人响应。

代理头仅从明确的 IP/CIDR 或验证过的 peer 接受，公网直连传入的 X-Forwarded-Host/Proto 不能改变站点身份。配置要明确代理是否保留或剥离路径前缀，支持其中一种固定契约并验证，不能两端都剥离。证书、域名所有权、canonical 跳转和 trusted origins 进入站点上线检查。

## 与现有网站共存

按照用户指定的参考，只借鉴 `guangyue-panel` 的共存原则、配置边界、预检查和回滚方法；不移植其业务架构。现有网络入口属于部署者，应用不能默认接管公网 80/443 或覆盖整份 Nginx 配置。详细出处见 [参考记录](multisite-reference.md)。

独立实例默认暴露可配置的回环 HTTP 端口，由已有 Nginx/Caddy/平台入口代理。多实例使用不同 Compose project name、内部端口和 volume 名称；不使用固定 container_name 造成冲突。若现有服务器已使用 TCP SNI/PROXY protocol 入口，应用接在现有 HTTPS HTTP 上游之后，明确链路契约；新项目不擅自迁移其他站点监听。

部署前只读检查端口、域名、既有代理块、TLS 终止位置、PROXY 头、路径前缀、目录权限和数据卷。变更只针对本项目的独立配置片段，先预览、测试，再由部署者启用；失败能还原该片段和应用版本。已有复杂入口不宣称一键自动重写。

## Compose 基础与扩容配置

以下是规划中的 profiles，没有生成 Compose 文件。

| 配置         | 服务                                                            | 适用范围                               |
| ------------ | --------------------------------------------------------------- | -------------------------------------- |
| basic        | app、PostgreSQL，发布前独立 migration/import job                | 单站或有限多站；现有代理提供 HTTPS     |
| shared-sites | app、PostgreSQL cluster/外部 PG、站点注册表与受控 provisioning  | 一个后端多站隔离，realm 与连接数有上限 |
| scale        | edge/LB、多 app 副本、worker、PostgreSQL、可选 PgBouncer、Redis | 并发读写、导入/测验/曲线计算增多时     |

basic 的任务可由 app 内的任务执行器处理，scale 用同一镜像不同 entrypoint 单独运行 worker。数据库任务/回执持久化，worker 用租约/锁取得任务；重启后任务可重试。迁移始终由单一发布任务运行，不能每个副本启动时竞相迁移或 seed。

app 不需要粘性会话：认证会话在对应站点 PostgreSQL 中；频繁静态请求由入口/CDN 缓存；对象文件放共享 provider。Redis 只承担可重建缓存和共享限流，不能成为用户学习记录的唯一存储。

PgBouncer 作为可选连接池，按锁定 Prisma/驱动组合验证连接模式、预编译语句与迁移连接；不能只加服务名称就宣称兼容。迁移/备份使用适当的直连或独立连接预算。多 DB 与多副本要限制活跃 realm 数、池大小、空闲超时和连接总额；不能每个请求新建 PrismaClient。

## 高并发的具体约束

| 压力点              | 设计处理                                                                                           |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| 查词/内容           | public cache key 包含 site/content release/query/locale；精确与索引查询；SQLite 在线程池中有界排队 |
| 用户进度            | 短事务、数据库唯一键、行锁或原子 revision 更新；相同词/用户只串行必要写入                          |
| 反复点击与重试      | site/user/commandId 幂等回执，重复请求不重复 FSRS 或计数                                           |
| 多副本限流          | Redis 或共享 DB 限额；不能只依赖各进程 Map                                                         |
| 熟词导入/导出       | 字节/条目限额、异步任务、分页/流式处理、批次一致性、每站公平配额                                   |
| 测验                | 固定试卷版本、答案索引和幂等提交；不在每题临时扫描全部词库                                         |
| 曲线/统计           | 增量聚合、固定采样点、版本快照、后台计算、私有缓存和截至时间                                       |
| 大热点与拥塞        | 有界队列、超时、取消、429/503 和重试建议；后台任务不能挤占所有在线写入连接                         |
| 站点 noisy neighbor | 每站请求/任务/DB 连接配额，跨站公平调度；对异常站点单独限流                                        |
| 发布与重启          | 就绪检查、优雅关闭、兼容 schema、队列租约到期恢复、备份与分阶段升级                                |

并发安全先依赖数据库约束，进程内锁只作优化。同一命令重试返回的旧回执应区分原始结果与当前进度，不让客户端把更晚 revision 倒退。个人响应不能被公共缓存；缓存无站点键或省略配置版本会造成内容串站。

## 容量目标与验证

用户尚未给出确切人数和硬件，因此这里不宣称可承载某个并发数。建议施工压测按 50/200/500 同时活跃学习用户递增，再针对实际预算确定发布容量；活跃用户数、在线连接数和每秒请求量分别报告。

候选服务目标为常用读接口 p95 低于 300ms、评价事务 p95 低于 500ms、受控负载错误率低于 0.5%；属于待确认的验收目标，不是当前结果。压测需保留固定硬件、数据包、数据库连接上限、请求混合和持续时间。

场景覆盖跨站并发、热点词、相同用户两设备冲突、批量导入与前台学习同时发生、曲线缓存命中/失效、worker 重启、Redis 不可用、PG 短暂断连、滚动升级和超限限流。验收以“不串站、不丢写、不重复计数、不无界排队”为硬条件；响应时间不达标时再调整池、索引、缓存、队列或拆执行器。
